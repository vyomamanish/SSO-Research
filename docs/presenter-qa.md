# Presenter Q&A: questions you will probably be asked

Short, technical answers with the file to point at. Each answer is true for this repository as it stands. Where something is not built, the answer says so: it's better to say "not built yet, here's the plan" than to guess.

Background: [`project-guide.md`](project-guide.md) (how it works) and [`migration-plan.md`](migration-plan.md) (existing users).

---

## The idea

**Q: In one sentence, what is this?**
Authentik becomes the one place that checks who someone is; OTT and DSG trust its signed ID tokens and keep their own data and sessions.

**Q: Why Authentik and not Auth0, Keycloak or Cognito?**
That choice came with the plans: both `ott-sso.md` and `dsg-sso.md` are written for Authentik. It's open source and self-hosted (no per-user fees, data stays with Vyoma), supports OIDC, SAML, MFA, passkeys, Google and back-channel logout, and is configured as code with blueprints. Keycloak would also work; the app code is plain OIDC, so it isn't tied to Authentik.

**Q: Is the app code tied to Authentik?**
Mostly no. Both apps use standard OIDC through `openid-client` and `jose`. Authentik-specific parts are the blueprints, the custom scope names (`vyoma_roles`, `dsg`) and the issuer URL format.

**Q: Why not one shared cookie for both apps?**
They're on different domains in production (and different ports locally), and browsers don't share cookies across domains. More importantly, each app needs its own session rules: OTT has 7-day sessions revoked per device, DSG has short staff sessions revoked per user. SSO means one *identity provider*, not one cookie.

## The protocol

**Q: Which OIDC flow, and why?**
Authorization code flow with PKCE, confidential clients. The code goes through the browser; tokens are fetched server to server with the client secret, so tokens never appear in a URL. Both plans recommend it.

**Q: What do PKCE, state and nonce each stop?**
PKCE: a stolen code can't be exchanged without the verifier. State: login CSRF (being logged in as the attacker). Nonce: replaying an old ID token. Code: `ott/src/app/api/auth/login/route.ts`, `dsg/backend/services/oidcClient.js`.

**Q: How does the app know the ID token is genuine?**
It checks the RS256 signature with Authentik's public keys from the JWKS endpoint, plus `iss` (exact, with trailing slash), `aud` (its own client ID) and `exp`. Only RS256 is accepted, so `alg: none` or HS256 tricks fail. `ott/src/lib/auth.ts` `verifyAuthentikToken`, `dsg/backend/services/oidcClient.js` `verifyAuthentikJwt`.

**Q: Doesn't openid-client already check the signature?**
It checks `iss`, `aud`, `exp` and `nonce`, but for the code flow over direct TLS it doesn't verify the signature. The plans ask for a JWKS check, so we do it explicitly.

**Q: What happens when Authentik rotates its signing key?**
`createRemoteJWKSet` caches the keys and refetches when it sees an unknown key ID, so rotation needs no app change.

**Q: Where are the client secrets?**
Server-side env files only (`ott/.env`, `dsg/backend/.env`), generated by `npm run setup`, git-ignored. Authentik reads the same values from `.env` through the blueprint (`!Env`). The DSG React app never has a secret; that's why DSG uses a backend-for-frontend.

**Q: What claims are in the ID token?**
`sub` (user UUID), `email`, `email_verified`, `name`, `preferred_username`, `sid`, and OTT's `role` or DSG's `dsg_roles`. The role claims come from our scope mappings in `blueprints/vyoma-sso-demo.yaml`.

**Q: Why is `sub` the same in both apps?**
Both providers use `sub_mode: user_uuid`. With the default (hashed per provider), the same person would get different IDs in each app.

## Sessions and logout

**Q: What is OTT's session now?**
An encrypted JWT (JWE, `dir` + `A256GCM`) in the HttpOnly `vyoma_session` cookie, 7 days, holding user ID, Authentik ID, email, role, `sid` and the ID token. It replaces the plain `user_email` cookie that anyone could forge. `ott/src/lib/session.ts`.

**Q: What is DSG's session now?**
Exactly the same HS256 token DSG issues today (`{ id, tokenVersion }`), 8 h for staff and 12 h for customers, in `sessionStorage`. Keeping it means the 40 frontend files that send the Bearer header don't change. `dsg/backend/utils/sessionToken.js`.

**Q: Why the 60-second one-time code in DSG?**
So the DSG token never appears in a redirect URL (history, logs, `Referer`). The callback stores a hashed, single-use code; the SPA swaps it with `POST /exchange`; `findOneAndDelete` makes it single use. `dsg/backend/routes/oidcRoutes.js`.

**Q: DSG's token is still readable by JavaScript. Isn't that a problem?**
Yes, it's the biggest remaining risk (DSG weakness W1). It's unchanged from today and is DSG's Phase 2: an HttpOnly cookie plus a Content-Security-Policy. Not built yet.

**Q: How does logout in one app log you out of the other?**
The app ends its own session, sends the browser to Authentik's end-session URL, and Authentik's worker POSTs a signed `logout_token` to the other app's back-channel endpoint. OTT revokes that `sid`; DSG bumps `tokenVersion`. Took about 1–2 seconds in testing.

**Q: Can someone forge a logout request?**
No. The logout token is verified like an ID token (JWKS signature, issuer, audience) plus `typ: logout+jwt` and the back-channel `events` claim. Tests sent forged tokens and they were rejected with 400.

**Q: If I copy someone's session before they log out, does it still work?**
No. OTT checks the `SessionRevocation` table on every request; DSG's `protect` compares `tokenVersion` with the database on every request. Both were tested with copied credentials.

**Q: Why does OTT revoke one session but DSG revokes all of the user's sessions?**
OTT's cookie carries Authentik's `sid`, so it can target one browser. DSG's token only has `{ id, tokenVersion }`, so its only lever is per user, which is also how DSG's existing "log out everywhere" works.

**Q: What if the back-channel call fails?**
The other app's session stays valid until it expires or the user logs out there. The app that started the logout is still logged out. In production, monitor back-channel errors in Authentik and make the endpoints reachable from Authentik.

## Roles and access

**Q: Where are roles managed now?**
As Authentik groups. OTT gets one `role` claim (`vyoma_roles` scope); DSG gets `dsg_roles`, the list of `dsg-*` groups. Both apps overwrite the stored role at every sign-in.

**Q: If I remove someone from a group, when do they lose access?**
At their next sign-in. An open session keeps the old role until it ends (OTT up to 7 days, DSG staff up to 8 hours). For immediate removal, end their sessions in Authentik, which back-channels both apps. A periodic re-check (DSG plan 4.5, OTT silent refresh) would close this gap; it's not built.

**Q: Can a user edit their role in the browser?**
No. OTT's role is inside an encrypted cookie and re-read from the database; DSG's roles are read from MongoDB on every admin request by `adminMiddleware`. The React admin guards are cosmetic; the API enforces it (Coupons returns 403 for Ravi).

**Q: What's the admin-guard bug you found?**
OTT checks Manager/Finance restrictions in `admin/layout.tsx`. The Next.js App Router doesn't re-render a layout when you click between its child pages, so the check only ran on the first admin page. A Manager opened Courses, clicked Users, and saw every customer. The fix is a check in each page (`ott/src/lib/adminGuard.tsx`). It's probably in production today, independent of SSO.

**Q: Why prefix groups with `vyoma-` and `dsg-`?**
So each app's roles don't collide and it's clear which app a group affects. The DSG plan recommends `<app>-<role>` naming.

## Existing users

**Q: Do existing users lose anything?**
No. Purchases, plans, progress and orders point at the app's own user ID, which doesn't change. Linking adds one field. Meera's demo record keeps everything and her IDs are unchanged.

**Q: How does an existing account get linked?**
At first SSO sign-in: match by Authentik ID, else by verified email (then save the Authentik ID), else create. See [`migration-plan.md`](migration-plan.md) section 6.

**Q: Couldn't someone register in Authentik with my email and take my account?**
Not with these rules: linking needs `email_verified: true`, and Authentik must have verified the address. An account already linked to another Authentik ID is refused. A customer identity can't take over a DSG admin record. The OTT plan didn't require a verified email; we added it.

**Q: What about passwords?**
OTT's unsalted SHA-256 hashes shouldn't be imported: move passwords just-in-time while old login is still on, then reset for the rest. DSG's bcrypt might be importable; test first. Google and guest accounts have nothing to move. Details in [`migration-plan.md`](migration-plan.md) section 5.

**Q: Did you build the user import?**
No. The linking rule, the new fields, and role sync are built and tested. The import script, the dry-run report, dual-login mode and the just-in-time password move are not built yet.

**Q: What if someone uses different emails in OTT and DSG?**
They get two Authentik accounts. It can't be detected automatically; support merges them on request.

**Q: Can we roll back?**
Yes. Sign-in is behind flags in both plans, linking only adds fields, and old password hashes are kept for the rollback window, so switching the flag back restores the old login immediately.

## Operations

**Q: What happens if Authentik goes down?**
People already signed in keep working: each app has its own session and doesn't call Authentik per request. Nobody new can sign in; OTT shows "Vyoma SSO isn't reachable right now". During the "both" phase the old login is still available. In production, Authentik needs HA, backups and monitoring.

**Q: How is Authentik configured? Can we reproduce it?**
Entirely by blueprints (`blueprints/*.yaml`). The worker applies them at startup and hourly. A fresh install is configured with no clicks, and the files are reviewed in git like code.

**Q: What does it cost to run?**
Authentik is open source. It needs its server, worker and PostgreSQL (no Redis in current versions). Hosting cost only.

**Q: How do we add a third app, like the intranet?**
Add a provider and application to the blueprint (client ID, secret, redirect URIs, scopes), and use the same OIDC code pattern. Users and groups already exist; `sub` will match.

**Q: Mobile and TV apps?**
Not in the prototype. The OTT plan's section 8 uses native PKCE (with the system browser) for mobile and the device authorization grant for TVs.

**Q: How was it tested?**
Playwright drove a real Chromium against real Authentik, both databases and both apps: 58 end-to-end checks (5 users, both logout directions, data kept, forged tokens, reused codes, open redirects), 15 Google-path checks with a Google-shaped stand-in, the 9-step demo script, and 18 DSG unit tests (`npm test`). Not tested: a real Google account, Windows/Linux hosts.

**Q: Why are there passwords in `.env`?**
They're generated random values for the local demo only, git-ignored and file mode 600. Nothing secret is committed.
